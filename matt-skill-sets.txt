# Matt Pocock skill sets

Lists consumed by `/setup-git-memory` and by scripts/package-claude-web-skills.sh.
Install with repeated `-s` flags and `-a universal`:

```bash
npx skills@latest add mattpocock/skills -s research -s tdd -a universal -y
```

Do **not** vendor `setup-matt-pocock-skills` — its output is what this scaffold
already wrote under `docs/agents/`.

## Choosing a set

Take `full` unless the target repository is small enough that a shorter list is the
point. `minimal` keeps the craft a feature cannot be delivered without — the
interview, the domain model, TDD, review, module design and the debugging loop —
and drops the six that serve situations you reach less often: a throwaway spike
(`prototype`), a conflicted merge (`resolving-merge-conflicts`), a periodic
architecture scan (`improve-codebase-architecture`), an effort that outgrows one
session's queue (`wayfinder`), the glossary-and-ADR variant of the interview
(`grill-with-docs`), and skill authoring (`writing-great-skills`).

Adding one later is a single `npx skills@latest add … -a universal -y` followed by
`./scripts/check-memory.sh --fix` to re-pin the vendored bytes.

## Not vendored, because this repository owns the stage

Six upstream skills were vendored before v2 and are not any more. Each was the
entry point for a stage this repository now drives itself, and two entry points
for one stage is how an agent picks the wrong one:

| Upstream | Superseded by | Why |
|----------|---------------|-----|
| `to-spec` | `/create-feature-spec` | Upstream writes one document; a spec here is four files plus a node header, and their presence is checked |
| `to-tickets` | `/plan-feature` | Five typed ticket boilerplates, `Blocked by:` edges, cycle detection and a scenario-coverage step upstream has no equivalent for |
| `implement` | `/implement-feature` | Upstream is fourteen lines, most of them "use /tdd" |
| `triage` | `docs/agents/triage-labels.md` | The label vocabulary is closed here and enforced by `check-memory.sh` |
| `handoff` | `M:handoff-pr` | Upstream writes the handoff to an OS temp directory, which does not survive a cloud agent's container |
| `wayfinder` (partial) | the work graph | Frontier, blockers and cycles are computed from node headers; the fog-clearing interview is still upstream's, so it stays in `full` |

`grilling`, `domain-modeling`, `tdd`, `code-review`, `codebase-design`,
`diagnosing-bugs`, `prototype`, `research`, `grill-with-docs`,
`resolving-merge-conflicts` and `improve-codebase-architecture` have no
equivalent here and are not going to get one. They answer *how to do the work
well*; this repository answers *where the output lands and what proves it*.

Which skill runs at which delivery stage, and which repo-authored skill is the entry
point that drives it, is one table with one home:
scaffold/docs/agents/delivery-workflow.md, "Which skill performs which stage". Read
it there — a second copy in this file would drift the first time a stage's entry
point changes. The adapter layer underneath it (what each upstream skill assumes,
and what this repository answers instead) is
scaffold/docs/agents/vendored-skills.md.

This file lists vendored skills only. The repo-authored skills under
`.cursor/skills/` are copied from `scaffold/`, not installed through the CLI.
